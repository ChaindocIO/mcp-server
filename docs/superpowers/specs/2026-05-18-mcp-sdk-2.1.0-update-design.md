# MCP server update for Chaindoc SDK v2.1.0 — design

**Date:** 2026-05-18
**Target package:** `@chaindoc_io/mcp-server`
**Current version:** `0.1.4` (SDK `^2.0.1`)
**Target version:** `0.2.0` (SDK `^2.1.0`)
**Source of truth:** `SERVER_SDK_API_REFERENCE.md` (SDK v2.1.0, verified live 2026-05-18)

---

## 1. Goals, scope, and versioning

### 1.1 Goal
Update `@chaindoc_io/mcp-server` to expose the full SDK v2.1.0 surface as MCP
tools, preserving the project's "thin, typed, 1:1 façade" identity. Add 67
new SDK-wrapper tools plus 1 verification-polling helper (68 total), modify
2 existing tools (`signatures.get_my_requests` schema, `signatures.sign`
description), add 5 new resource URIs, 3 new prompts, structured
state-machine error hints, and hybrid binary-download support. Itemized
totals in §2.11.

### 1.2 Non-goals
- No client-side business logic beyond what the SDK already does (email
  normalization, `Date` serialization, retry).
- No new transports (stdio + HTTP stay as-is).
- No webhook delivery configuration (out of scope by SDK design; the server
  still only **verifies** inbound deliveries).
- No retroactive change to existing tool input/output shapes — adds only.
- No live-API integration tests added in this PR. Unit tests + type-check
  against the SDK types are the structural backstop.

### 1.3 Versioning
- `package.json` `version`: `0.1.4` → `0.2.0`.
- `package.json` dependency `@chaindoc_io/server-sdk`: `^2.0.1` → `^2.1.0`.
- `src/server.ts` `buildServer` server name version string: `0.1.0` → `0.2.0`.
- `chaindoc.plugin` and `chaindoc-claude/.claude-plugin/plugin.json` track the
  same `0.2.0`.

### 1.4 Compatibility
All ~35 existing tools keep their names and schemas.
`chaindoc_signatures_sign` description is rewritten to bias agents toward
`chaindoc_contracts_business_sign`, but the tool stays callable.
`chaindoc_signatures_get_my_requests` schema gains an optional `status`
filter — strictly additive (existing callers continue to work).

## 3. Binary download infrastructure

Eight new tools return SDK `DownloadResult` (`{ data: ArrayBuffer;
contentType: string; fileName?: string }`):

- `documents.download`, `documents.preview`
- `signatures.downloadCertificate`, `signatures.downloadSignedDocument`
- `invoices.downloadPdf`
- `templates.previewPdf`, `templates.previewUnsavedPdf`

(`templates.previewHtml` returns plain JSON `{ html }` and uses the standard
JSON tool path.)

### 3.1 New module — `src/core/downloads.ts`

```ts
export type DownloadAdapterMode = "auto" | "disk" | "inline";

export interface DownloadAdapterConfig {
  mode: DownloadAdapterMode;
  dir: string;
  inlineMaxBytes: number;
}

export interface DiskResult {
  kind: "disk";
  path: string;
  contentType: string;
  fileName?: string;
  sizeBytes: number;
  sha256: string;
}

export interface InlineResult {
  kind: "inline";
  base64: string;
  contentType: string;
  fileName?: string;
  sizeBytes: number;
  sha256: string;
}

export async function deliverDownload(
  cfg: DownloadAdapterConfig,
  res: DownloadResult,
  hint: { tool: string; suggestedExt?: string },
): Promise<DiskResult | InlineResult>;
```

### 3.2 Mode resolution
- `stdio` transport → effective mode `disk` (local agent shares filesystem).
- `http` transport → effective mode `inline` (remote agent does not).
- Override via `CHAINDOC_DOWNLOAD_MODE=auto|disk|inline`. `auto` reproduces
  the per-transport default.
- `inline` path enforces `sizeBytes ≤ inlineMaxBytes`. Over the cap, the
  adapter throws a `payload_too_large` structured error (see §4) with a hint
  pointing at `CHAINDOC_INLINE_DOWNLOAD_MAX_BYTES`.

### 3.3 Disk path
- `dir` is created on first write (`fs.mkdir(dir, { recursive: true, mode: 0o700 })`).
- Filename: prefer `res.fileName`; otherwise `<tool>-<uuid>.<ext>`, ext
  inferred from `contentType` (`application/pdf` → `pdf`,
  `image/png` → `png`, …) or `hint.suggestedExt`.
- Returns absolute `path` plus content-addressed `sha256` so the agent can
  confirm what it received.
- No automatic cleanup in v0.2.0. Documented in README. A future GC job is
  a roadmap item, not in scope here.

### 3.4 Wiring
- `BuildServerOptions` gains:
  `downloads?: { mode?: DownloadAdapterMode; dir?: string; inlineMaxBytes?: number }`.
- Each transport (`src/transports/stdio.ts`, `src/transports/http.ts`) seeds
  the default mode from itself before calling `buildServer`.
- `src/core/config.ts` adds three zod-coerced fields with defaults:
  `downloadMode`, `downloadDir`, `inlineDownloadMaxBytes`.
- `ToolContext` in `src/tools/types.ts` gains `downloads:
  DownloadAdapterConfig` so each binary tool can call `deliverDownload(ctx.downloads, ...)`
  without reaching into the client.

### 3.5 Representative tool

```ts
export const documentsDownload = defineTool({
  name: "chaindoc_documents_download",
  description:
    "Download a document version's bytes. On stdio transport returns " +
    "{ kind: 'disk', path, ... }; on HTTP transport returns " +
    "{ kind: 'inline', base64, ... } up to CHAINDOC_INLINE_DOWNLOAD_MAX_BYTES.",
  inputSchema: z.object({ versionId: z.string().uuid() }),
  handler: (args, { client, downloads }) =>
    client.run("chaindoc_documents_download", async (sdk) =>
      deliverDownload(downloads, await sdk.documents.download(args.versionId), {
        tool: "chaindoc_documents_download",
      }),
    ),
});
```

### 3.6 README env table additions

| Env var | Default | Notes |
|---|---|---|
| `CHAINDOC_DOWNLOAD_MODE` | `auto` | `auto` \| `disk` \| `inline`. |
| `CHAINDOC_DOWNLOAD_DIR` | `<os.tmpdir>/chaindoc-mcp` | Used when mode resolves to `disk`. |
| `CHAINDOC_INLINE_DOWNLOAD_MAX_BYTES` | `4194304` (4 MB) | Caps inline base64 size; over → `payload_too_large`. |

## 4. Structured error envelope + verification helper

### 4.1 Error envelope evolution — `src/core/errors.ts`

Current envelope:

```ts
{ code, message, httpStatus?, retryAfter?, requestId?, details? }
```

`code` is purely status-derived. SDK doc §4 says most `400`/`403` responses
are state-machine rejections. We refine without breaking — add a finer
`code` set, plus `hint` and `validation` fields:

```ts
export type ChaindocErrorCode =
  | "invalid_argument"
  | "unauthenticated" | "forbidden" | "not_found" | "conflict"
  | "unprocessable" | "rate_limited" | "upstream_error"
  | "not_implemented" | "internal_error"
  | "payload_too_large"          // new — download adapter (§3)
  // ─── new, state-machine codes
  | "wrong_state"                // 400 "Only draft invoices can be sent", "DRAFT only" ops
  | "not_verified"               // 400 "Version is not verified"
  | "wrong_party"                // 400 "You cannot approve your own request"
  | "stripe_not_ready"           // 400 contract create when Stripe Connect not ready
  | "document_not_public";       // 400 sendPublicLink on non-public document

export interface ChaindocMcpError {
  code: ChaindocErrorCode;
  httpStatus?: number;
  message: string;
  validation?: unknown;
  hint?: string;
  retryAfter?: number;
  requestId?: string;
  details?: unknown;
}
```

### 4.2 Refinement strategy
`toChaindocMcpError` performs two passes:

1. **Status pass** (existing) — HTTP status → generic code.
2. **Pattern pass** (new) — when the SDK error's `response` envelope carries
   a known string-message pattern, override the generic code with a
   state-machine code and attach a `hint`.

Patterns live in `src/core/error-patterns.ts` as an ordered array of
`{ statusEquals, messageRegex, code, hint }` rules.

Initial pattern set (sourced from SDK doc §4 + §5):

| `statusEquals` | `messageRegex` (case-insensitive) | `code` | `hint` |
|---|---|---|---|
| 400 | `^Version is not verified` | `not_verified` | `Call chaindoc_documents_wait_for_verification with the versionId before retrying.` |
| 400 | `cannot approve your own request` | `wrong_party` | `Only the counterparty can approve a mutual-approval termination request.` |
| 400 | `Only draft invoices can be sent` | `wrong_state` | `Invoice is not in 'draft'. Inspect with chaindoc_invoices_get; only draft invoices accept send/update.` |
| 400 | `Document is not public` | `document_not_public` | `Call chaindoc_documents_update_rights with accessType='public' first.` |
| 400 | `DRAFT only\|status is not draft\|must be in draft` | `wrong_state` | `Operation requires the contract to be in DRAFT.` |
| 400 | `Stripe Connect` | `stripe_not_ready` | `Workspace owner must complete Stripe Connect onboarding in the Chaindoc dashboard.` |

### 4.3 Array-message handling
SDK doc §2.2: when the backend returns a validation array, the SDK puts a
generic string in `error.message` and the real array in
`error.response.message`. The refinement now lifts that array into
`validation` (instead of leaving it in `details`) when present.

### 4.4 Per-tool description trailers
Each state-guarded tool gains a one-line "Preconditions:" trailer mirroring
§4 of the SDK doc. Examples:

- `chaindoc_contracts_update`: `Preconditions: contract must be in DRAFT. State mismatches return code='wrong_state'.`
- `chaindoc_signatures_create_request`: `Preconditions: document version must be blockchain-verified. Returns code='not_verified' otherwise — use chaindoc_documents_wait_for_verification.`
- `chaindoc_contracts_termination_approve`: `Preconditions: must be called by the counterparty, not the initiator. Returns code='wrong_party' otherwise.`

These trailers are what bias the LLM to pick the right tool for the current
state.

### 4.5 Verification polling helper

One new tool — the only one in this update that contains client-side
control flow beyond a single SDK call:

```ts
export const documentsWaitForVerification = defineTool({
  name: "chaindoc_documents_wait_for_verification",
  description:
    "Block until a document version's blockchain anchor is verified (or " +
    "timeoutMs elapses). Use after chaindoc_documents_create with status='published' " +
    "and before chaindoc_signatures_create_request. Polls " +
    "chaindoc_documents_get_verification_status every intervalMs.",
  inputSchema: z.object({
    versionId: z.string().uuid(),
    timeoutMs: z.number().int().positive().max(120_000).default(60_000),
    intervalMs: z.number().int().positive().min(500).max(10_000).default(2_000),
  }),
  handler: async (args, { client }) => {
    const deadline = Date.now() + args.timeoutMs;
    while (Date.now() < deadline) {
      const status = await client.run("documents.wait_for_verification.poll", (sdk) =>
        sdk.documents.getVerificationStatus(args.versionId),
      );
      if ((status as { verified?: boolean }).verified === true) {
        return { verified: true, status };
      }
      await new Promise((r) => setTimeout(r, args.intervalMs));
    }
    return {
      verified: false,
      timedOut: true,
      message:
        "Version not verified within timeout. The blockchain anchor may still be in flight; retry the same poll later.",
    };
  },
});
```

Each poll goes through `client.run`, so it consumes from the shared token
bucket (10/60s). The default `intervalMs` (2 s) stays above the bucket
refill cadence; aggressive low values will simply block on the bucket.

## 5. Resources & prompts additions

### 5.1 Resources — `src/resources/index.ts`
Five new URIs mirroring the new SDK list/get endpoints useful for
`@-mention` discovery:

| URI | Description | SDK call |
|---|---|---|
| `chaindoc://templates` | Recent templates | `sdk.templates.list({ page: 1, limit: 25 })` |
| `chaindoc://templates/{id}` | One template (current + last-published version, variables schema) | `sdk.templates.get(id)` |
| `chaindoc://invoices` | All invoices for the key owner (cross-contract) | `sdk.invoices.listAll({ page: 1, limit: 25 })` |
| `chaindoc://contracts/{id}/stats` | Financial aggregate for one contract | `sdk.contracts.getStats(id)` |
| `chaindoc://contracts/{id}/termination` | Current/most-recent termination request | `sdk.contracts.termination.get(id)` |

Wiring follows the existing pattern: add to the static `items` list at the
top of `listResources`, add a regex case in `readResource` for the
templated URIs, enrich `items` with concrete IDs by best-effort calls (swallow
failures, like the contract/sigreq enrichments today).

Intentionally skipped: per-contract `signing-requests` sub-lists, the new
sub-modules `payment-terms` / `agreements`, activity/downloads logs.

### 5.2 Prompts — `src/prompts/index.ts`
Three new prompts for the multi-step lifecycle flows where SDK doc §4
state-machine traps make a guided prompt genuinely useful:

1. **`manage_contract_termination`** — args: `contractId`, optional
   `terminationType` hint. Flow: check `contracts.termination.getStatus`
   for outstanding invoices and `canInitiateTermination`; choose
   `one_side` vs `mutual_approval`; call `contracts.terminate`; if
   `mutual_approval`, explain that the counterparty (not the initiator)
   must approve; surface `wrong_party` errors clearly.
2. **`author_and_publish_template`** — args: optional `templateId` (if
   revising). Flow: pick or create (`templates.create` with category +
   Tiptap `contentJson` + `variablesSchema` + `signerSlots`); preview via
   `templates.preview_html` / `preview_pdf`; iterate; `templates.publish`;
   explain that editing a published template forks a new draft version
   while the last-published version remains the renderable one until the
   next publish.
3. **`bill_recurring_on_imported_contract`** — args: `contractId` (must be
   an `import`-origin active contract). Flow: confirm the contract was
   imported (`contracts.get`); design `paymentTerms[]`; call
   `contracts.setup_recurring`; explain that billing only starts once
   the contragent accepts the emailed approval and links a payment method;
   show how to resend / cancel the pending approval.

Intentionally skipped: single-CRUD prompts (add payment term, cancel
signature request, remind, etc.) — the tool description is enough.

### 6.3 Patterns kept
- Hand-rolled `fakeLogger()` + `fakeClient(sdk)` injecting a partial
  `ChaindocSdkLike`.
- `vi.fn().mockResolvedValue(...)` for SDK methods, then assert call args.
- Zod schemas tested for accept/reject directly (no client round-trip).

### 6.4 Per-tool unit-test recipe
Applied to every new tool, no exceptions:

1. **Schema parses good input** — happy path with optional fields both
   omitted and set.
2. **Schema rejects key invalid input** — invalid UUID/email/hash; missing
   required; enum out-of-range. One case per non-obvious validation.
3. **Handler forwards correctly** — `fakeClient` records the SDK call;
   assert path arguments and body shape; assert `Date`-typed body fields
   are actually `Date` instances (covers `deadline`, `startDate`/`dueDate`
   in `payment_terms_create`, etc.).
4. **Handler unwraps nested args** — for tools with `contractId` + body
   fields, assert path/body separation.

### 6.5 Cross-cutting tests
- **`downloads.test.ts`** — three modes (disk, inline, inline-over-cap).
  Disk mode uses a `vitest`-managed temp dir, cleaned in `afterEach`.
  Assertions: file written under `dir`; correct `sha256`; extension
  inferred from `contentType`; `payload_too_large` thrown when
  `sizeBytes > inlineMaxBytes`.
- **`error-patterns.test.ts`** — fixture-based. For each of the 6 patterns
  in §4.2, feed a synthetic `ChaindocError`-shaped object and assert the
  refined `{ code, hint }`. Plus: array-message case lifts the array into
  `validation`.
- **`wait-for-verification.test.ts`** — uses `vi.useFakeTimers()`. Three
  cases: verified on first poll; verified after N polls; timeout returns
  `{ verified: false, timedOut: true }` and does not throw.
- **`tools.test.ts`** — existence check: every tool in `allTools` has a
  unique name, description ≥ 40 chars, and an input schema that is a
  `ZodType`.

### 6.6 Integration tests
`npm run test:integration` stays opt-in. We do **not** add live-API
integration tests in this PR. Unit tests + `ChaindocSdkLike` type-pinning
in `src/core/client.ts` give a compile-error backstop for SDK shape drift.

### 6.7 Manual smoke list (README "Develop" section)
Documented, not automated. Run via `npm run inspect` against an `sk_` key

- **Contract lifecycle:** `contracts.create_minimal` → `attach_document` →
